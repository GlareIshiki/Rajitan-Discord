# 8. アーキテクチャ問題レポート

Rajitan-Discord / Rajitan-WebUI の現行構成を比較調査し、特定されたアーキテクチャ上の問題点をまとめる。

## 調査対象

| リポジトリ | 役割 | デプロイ先 |
|---|---|---|
| **Rajitan-Discord** | Bot本体 + FastAPI バックエンド | XServer VPS (systemd) |
| **Rajitan-WebUI** | Next.js フロントエンド | Vercel |

```
ユーザー → Rajitan-WebUI (Vercel)
              ↓ API (https://api.glareishiki.com)
           Rajitan-Discord (VPS)
              ├── FastAPI (localhost:8000)
              ├── Discord Bot (discord.py)
              ├── SQLite / Redis
              └── DeepSeek v3 / OpenAI
```

---

## 問題一覧

| # | 優先度 | 問題 | 影響 |
|---|--------|------|------|
| 1 | **高** | Bot + API 同一プロセス | 片方のクラッシュで全停止 |
| 2 | **高** | 認可チェック不足 | 他ギルドのデータへの不正アクセス |
| 3 | **中** | Redis なし時のメモリ揮発 | 再起動で短期・中期記憶消失 |
| 4 | **中** | SQLite 同時書き込み | 負荷増加時にロック競合 |
| 5 | **低** | 楽観的更新の失敗非通知 | データ不整合の可能性 |

---

## 1. Bot + API 同一プロセス【高】

### 現状

`main.py` の `RajitanApplication` が Discord Bot と FastAPI を `asyncio.gather()` で同一プロセス内に並行起動している。

```python
# rajitan/main.py
await asyncio.gather(
    bot.start(token),
    uvicorn.Server(config).serve()
)
```

### 問題点

- Bot 側の未処理例外やメモリリークで FastAPI も巻き添えクラッシュする
- API への高負荷（WebUI からの大量リクエスト）が Bot の応答遅延を招く
- systemd の自動再起動で両方が同時にダウン → WebUI が一時的に完全停止

### 対策案

- **プロセス分離**: Bot と FastAPI を別 systemd サービスに分離
- **共有ストレージ経由の通信**: SQLite / Redis をプロセス間の共有層として使用
- **段階的対応**: まず FastAPI を別サービスとして切り出し、Bot との通信は DB 経由に

---

## 2. 認可チェック不足【高】

### 現状

FastAPI の認証は `rajitan/web/auth.py` の `get_current_user()` で Discord OAuth トークンを検証している。ユーザーが「有効な Discord アカウントであること」は確認されるが、**対象リソースへのアクセス権限**は検証されない。

```python
# rajitan/web/routes/bot.py:128-147
@router.get("/guilds/{guild_id}/settings")
async def get_guild_settings(guild_id: str, user=Depends(get_current_user)):
    # ギルドが Bot に存在するかのみチェック
    guild = bot.get_guild(int(guild_id))
    if not guild:
        raise HTTPException(status_code=404, detail="Guild not found")
    # → user がこのギルドのメンバーかは未検証
```

### 問題点

- 認証済みの任意の Discord ユーザーが、所属していないギルドの設定を閲覧・変更可能
- LeveMagi データ（`/api/levemagi/*`）はギルド紐付けすらなく、全データが全ユーザーに公開
- カレンダーイベント（`/api/calendar/*`）も同様

### 影響範囲

| エンドポイント | 認可チェック |
|---|---|
| `GET/PUT /guilds/{id}/settings` | ギルド存在のみ、メンバーシップ未検証 |
| `GET/POST/PUT/DELETE /levemagi/*` | 認証のみ、データ所有者未検証 |
| `GET/POST/PUT/DELETE /calendar/*` | 認証のみ、データ所有者未検証 |

### 対策案

- **ギルドメンバーシップ検証**: Discord API (`/guilds/{id}/members/{user_id}`) でメンバー確認。キャッシュして負荷軽減
- **データ所有者チェック**: LeveMagi / Calendar にユーザー ID カラムを追加し、自分のデータのみ操作可能に
- **ロールベース認可**: ギルド設定変更はサーバー管理者（`ADMINISTRATOR` 権限持ち）のみ許可

---

## 3. Redis なし時のメモリ揮発【中】

### 現状

Redis 未接続時、`RedisClient` はメモリ辞書（`dict`）にフォールバックする。このフォールバックデータはプロセスメモリ上にのみ存在する。

### 問題点

- プロセス再起動（クラッシュ、デプロイ、systemd restart）で以下が全消失:
  - **Tier 1（ワーキングメモリ）**: クイズ回答待ち、確認待ち状態
  - **Tier 2（アクションログ）**: 直近の行動履歴
  - **会話データ**: チャンネルごとの会話履歴
- ユーザーから見ると「クイズに答えようとしたら忘れられていた」等の体験劣化

### 対策案

- **Redis の常時稼働を推奨構成に**: VPS に Redis をインストール・常時起動
- **フォールバック時の永続化**: メモリ dict を定期的に SQLite に書き出すスナップショット機構
- **クリティカルデータのみ SQLite 保存**: pending_action 等の重要状態は Redis 有無に関わらず SQLite に保存

---

## 4. SQLite 同時書き込み【中】

### 現状

Bot（エージェントのメモリ書き込み、会話ログ等）と FastAPI（WebUI からの LeveMagi CRUD、設定変更等）が同一の `rajitan.db` に同時アクセスする。

### 問題点

- SQLite はシングルライターモデル。同時書き込みで `SQLITE_BUSY` エラーが発生しうる
- aiosqlite は内部でスレッドプールを使用するが、書き込みロックは OS レベルで排他
- WAL (Write-Ahead Logging) モードの有効/無効が未確認

### 対策案

- **WAL モード有効化**: `PRAGMA journal_mode=WAL` で読み書き並行性を向上（確認・設定）
- **busy_timeout 設定**: `PRAGMA busy_timeout=5000` でロック待ちの猶予を設定
- **長期的にはDB分離**: Bot 用と API 用で DB ファイルを分けるか、PostgreSQL 等へ移行

---

## 5. 楽観的更新の失敗非通知【低】

### 現状

WebUI の `useLeveMagi` フックは楽観的更新（Optimistic Update）パターンを採用。クライアント側の状態を即座に更新し、API への同期はバックグラウンドで fire-and-forget で行う。

### 問題点

- API 呼び出しが失敗してもエラーが表示されない（コンソールログのみ）
- ユーザーには操作が成功したように見えるが、次回ページリロードでデータが巻き戻る
- ネットワーク不安定時やサーバーダウン時に顕著

### 対策案

- **トースト通知**: API 失敗時にユーザーに通知し、ローカル状態をロールバック
- **リトライ機構**: 失敗した操作をキューに入れて自動リトライ
- **同期状態の表示**: 「保存中」「同期済み」「未同期」のインジケーターを UI に追加

---

## 総合評価

現時点では個人〜小規模利用のため、実運用上で即座に問題になるケースは限定的。ただし、**認可チェックの不足（#2）はセキュリティ上の脆弱性**であり、公開 API として運用する以上は早急な対応が望ましい。Bot + API のプロセス分離（#1）は中長期的な安定性に直結するが、対応コストが高いため段階的に進めるのが現実的。
