# マルチエージェントチームシステム 設計書

## Context

Rajitanの単一エージェントアーキテクチャは、1リクエストに対して1つのLLMが逐次的にツール実行を繰り返す構造。複数の独立したタスク（例:「会話要約して、あとスケジュールも教えて」）を受けた場合でも、直列に1つずつ処理するため時間がかかる。

Claude Code Agent Teamsの設計パターンに着想を得て、複雑なリクエストを**並列サブエージェント**で処理する機構を導入する。

**目標:** 複数の独立タスクを含むリクエストを、内部で自動分解→並列実行→結果統合し、応答速度と品質を向上させる。ユーザーからは従来通り単一の「らじたん」に見える。

---

## 1. アーキテクチャ全体像

```
ユーザー → AgentOrchestrator.execute()
  │
  ├── team.enabled && リクエスト解析
  │     │
  │     ├── 複雑（並列可能） → TeamCoordinator.try_team_execute()
  │     │     │
  │     │     ├── TaskPlanner.decompose()
  │     │     │     LLM呼出でサブタスクに分解（non-thinking, temp=0.3）
  │     │     │     └── 分解不要 → should_use_team=False → 単一エージェントへ
  │     │     │
  │     │     ├── asyncio.gather(SubAgent×N)
  │     │     │     各サブエージェントが独立したコンテキストで並列実行
  │     │     │
  │     │     └── TaskPlanner.synthesize()
  │     │           結果統合、キャラクター口調で最終応答生成
  │     │
  │     └── 単純 → 従来の単一エージェントループ
  │
  └── team.enabled == false → 従来の単一エージェントループ（変更なし）
```

## 2. モジュール構成

```
rajitan/agent/team/
  ├── __init__.py
  ├── coordinator.py    TeamCoordinator — オーケストレーション
  ├── planner.py        TaskPlanner — タスク分解 + 結果統合
  └── sub_agent.py      SubAgentRunner — 軽量エージェントループ
```

## 3. 処理フロー詳細

### 3.1 タスク分解（TaskPlanner.decompose）

LLMに以下を入力し、JSON形式でサブタスク一覧を取得する:
- ユーザーのリクエスト文
- 利用可能なツール一覧（send_message/add_reactionを除外）

**分解しないケース（should_use_team=False）:**
- メッセージが30文字未満
- 挨拶・雑談・1ツールで完結するリクエスト
- タスク間に依存関係がある（前の結果が次に必要）
- LLMが分解不要と判定
- サブタスクが1個以下
- JSON解析失敗

**出力データ構造:**
```python
@dataclass
class SubTask:
    id: str                     # "task_1"
    description: str            # サブタスクの説明
    relevant_tools: List[str]   # このタスクで使うツール名
    priority: int = 0           # 統合時の順序

@dataclass
class DecompositionResult:
    should_use_team: bool
    sub_tasks: List[SubTask]
    reasoning: str = ""         # 分解理由（ログ用）
```

### 3.2 並列サブエージェント実行（SubAgentRunner）

各サブエージェントは独立した軽量エージェントループを実行する。

| 項目 | メインエージェント | サブエージェント |
|---|---|---|
| max_steps | 15 | 8 |
| thinking mode | 適応（complex→on） | 常にoff |
| ツール | 全36+ | タスク関連のみ |
| メッセージコンテキスト | 共有 | 独立 |
| call_counts | 共有（_call_counts） | ローカルdict |
| メモリ書き込み | あり | なし |
| Discord操作 | 可能 | 不可 |
| コンテキスト上限 | 80K tokens | 30K tokens |

**サブエージェントの制約:**
- `send_message`/`add_reaction` は使用不可（フィルタで排除）
- 各ツール呼び出しは1サブエージェントあたり最大3回
- 最終ステップではツール無効化、テキスト応答を強制
- タイムアウト（デフォルト60秒）で強制終了

**出力:**
```python
@dataclass
class SubAgentResult:
    task_id: str
    description: str
    success: bool
    data: str = ""              # 構造化結果（ユーザー向け文章ではない）
    tools_used: List[str]
    steps_taken: int = 0
    total_tokens: int = 0
    error: Optional[str] = None
```

### 3.3 結果統合（TaskPlanner.synthesize）

全サブエージェントの結果を受け取り、LLMでらじたんのキャラクター口調に統合:
- 各サブタスクの成功/失敗と結果データを入力
- キャラクター設定（persona）を注入
- 「サブエージェント」「チーム」等の内部用語は使わない
- non-thinking、temp=0.7

### 3.4 フォールバック

以下のすべてのケースで単一エージェントモードにフォールバック:
- 分解LLMが空レスポンスを返した
- JSON解析失敗
- サブタスク数が0-1個
- 全サブエージェントがタイムアウト
- 統合LLMが空レスポンスを返した

## 4. 設定（workflows/default.yaml）

```yaml
team:
  enabled: false                    # true で有効化
  max_sub_agents: 3                 # 最大サブエージェント数
  sub_agent_max_steps: 8            # サブエージェントの最大ステップ
  sub_agent_timeout_seconds: 60.0   # タイムアウト（秒）
  sub_agent_temperature: 0.7
  sub_agent_max_tokens: 1500
  decompose_max_tokens: 800
  decompose_temperature: 0.3        # 低温: 正確な分解
  synthesize_max_tokens: 1500
  synthesize_temperature: 0.7
  min_message_length: 30            # この文字数未満はチーム不使用
```

## 5. 並列安全性

### ToolRegistry.execute() の call_counts パラメータ

サブエージェントが並列実行する際、共有の `ToolRegistry._call_counts` を使うとカウント競合が起きる。

**解決策:** `execute()` にオプションの `call_counts` パラメータを追加。

```python
async def execute(self, name, disabled=None, call_counts=None, **kwargs):
    counts = call_counts if call_counts is not None else self._call_counts
    # counts を使って上限チェック・インクリメント
```

- メインエージェント: `call_counts=None` → 従来通り共有カウンター
- サブエージェント: `call_counts=local_dict` → 独立カウンター

## 6. 実行ログイベント（WebUI対応）

| event_type | タイミング | content |
|---|---|---|
| `team_decompose_start` | 分解開始 | — |
| `team_skip` | 単一エージェント推奨 | 理由 |
| `team_decompose_done` | 分解完了 | サブタスク数 |
| `team_parallel_start` | 並列実行開始 | — |
| `team_sub_agent_done` | 各サブエージェント完了 | task_id, 成否, ステップ数 |
| `team_synthesize_start` | 統合開始 | — |
| `team_complete` | チーム実行完了 | 所要時間, トークン数 |

## 7. 具体例

### 例1: 並列化が有効なケース
```
ユーザー: 「最近の会話をまとめて、あと今日のスケジュールも教えて」

分解結果:
  task_1: 「最近の会話を要約する」 → [summary, get_conversation]
  task_2: 「今日のスケジュールを取得する」 → [schedule_list, get_current_time]

並列実行:
  SubAgent A: get_conversation → summary → 結果テキスト
  SubAgent B: get_current_time → schedule_list → 結果テキスト

統合:
  「最近の会話ではXXの話題で盛り上がってたね！
   今日のスケジュールは...」
```

### 例2: 分解しないケース
```
ユーザー: 「曲かけて」
→ 30文字未満 → should_use_team=False → 単一エージェントでmusic_play実行

ユーザー: 「こんにちは」
→ 短文 → should_use_team=False → 単一エージェントで直接応答

ユーザー: 「会話を要約して、その内容でクイズ出して」
→ 依存関係あり（要約結果がクイズに必要） → should_use_team=False
```
