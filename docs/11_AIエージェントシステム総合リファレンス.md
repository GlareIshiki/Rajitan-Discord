## 1. 全体アーキテクチャ

### 処理の全体像

```
Discord メッセージ
  │
  ▼
RajitanBot (bot/client.py) — ルーティング判定
  │
  ├── pending_action あり → メンション不要でエージェント起動
  ├── @メンション検出     → エージェント起動
  └── 会話ウィンドウ内    → ResponseGate.should_participate() → yes/skip/leave
      │
      ▼
AgentOrchestrator.execute() — メインエージェントループ
  │
  ├── [判定1] Agent Teams 有効 & 複雑なリクエスト？
  │     └── YES → AgentTeamCoordinator（役割ベース協調）
  │
  ├── [判定2] サブエージェント有効 & 並列可能？
  │     └── YES → TeamCoordinator（並列独立タスク）
  │
  └── [判定3] 単一エージェントループ
        │
        ├── LLM呼び出し（DeepSeek v3 + function calling）
        ├── ツール実行 → 結果をコンテキストに追記
        ├── ループ継続 or 最終応答
        └── 最大15ステップで強制終了
      │
      ▼
ResponseGate.should_send() — 応答品質チェック
      │
      ▼
Discord 送信
```

### 3段階の実行モード判定

orchestrator.pyは以下の順序で判定する:

| 優先度 | モード | パッケージ | 用途 |
|---|---|---|---|
| 1 | Agent Teams | `agent/teams/` | 異なる専門ロールが依存関係つきで協調 |
| 2 | サブエージェント | `agent/team/` | 独立タスクを同一ワーカーで並列実行 |
| 3 | 単一エージェント | `agent/orchestrator.py` | 通常のエージェントループ |

いずれの上位モードもフォールバック時は次の段階に落ちる。

## 2. メッセージルーティング

### エントリーポイント: `bot/client.py`

Discordメッセージを受け取り、エージェントに渡すまでのフロー。

#### ルーティング条件（優先度順）

```python
async def on_message(message):
    # 1. 常に会話追跡
    conversation_tracker.track_message()

    # 2. メモリベースルーティング（pending_action）
    if memory_manager.has_pending_action(channel_id):
        → エージェント起動（メンション不要）

    # 3. @メンション検出
    if bot がメンションされている:
        → handle_mention() → エージェント起動

    # 4. 会話ウィンドウ内（メンション後2分間）
    if 会話ウィンドウがアクティブ:
        result = response_gate.should_participate()
        → "yes": エージェント起動
        → "skip": 無視
        → "leave": ウィンドウ終了
```

#### メモリベースルーティング

`has_pending_action()` による自然なマルチターン:

```
User: 「クイズ出して」          → @メンション
Bot:  [クイズ問題]              → set_pending_action(QUIZ_ANSWERS)
User: 「A」                     → メンションなし、pending_actionで起動
Bot:  [正解！解説は...]         → clear_pending_actions()
```

#### 会話ウィンドウ

- @メンション後、`CONVERSATION_WINDOW_SECONDS`（デフォルト120秒）間アクティブ
- ウィンドウ内では `ResponseGate.should_participate()` で参加判定
- `LEAVE` 判定で即時ウィンドウ終了

## 3. エージェントオーケストレーター

**ファイル**: `rajitan/agent/orchestrator.py`

### データ構造

```python
@dataclass
class AgentContext:
    guild_id: str           # サーバーID
    channel_id: str         # チャンネルID
    user_id: str            # ユーザーID
    username: str           # 表示名
    message: discord.Message  # Discord メッセージオブジェクト

@dataclass
class AgentResult:
    response: str           # ユーザーへの最終応答テキスト
    success: bool
    steps_taken: int
    tools_used: List[str]
    total_tokens: int
    goal: Optional[str]     # 元のリクエスト
```

### エージェントループの詳細

```python
async def execute(user_message, context) -> AgentResult:
    # 1. ワークフロー取得（ベース + ユーザーオーバーレイ）
    wf = workflow_loader.get_effective_config(guild_id, user_id)

    # 2. 上位モード判定
    #    → Agent Teams → サブエージェント → 単一ループ

    # 3. Thinking mode判定
    use_thinking = _looks_complex(user_message, wf)

    # 4. システムプロンプト構築
    system_prompt = prompt_builder.build_system_prompt(context)

    # 5. ツール定義取得（無効化ツールを除外）
    tool_definitions = tools.get_function_definitions(exclude=disabled_tools)

    # 6. エージェントループ（最大 max_steps 回）
    for step in range(max_steps):
        # コンテキスト圧縮チェック
        # ステップインジェクション（反省/緊急/最終）
        # LLM呼び出し
        # → テキスト応答 → ループ終了
        # → ツール呼び出し → 実行 → 結果追記 → ループ継続

    # 7. メモリ書き込み
    memory_writer.process_result(result, context)
```

### 適応的動作

#### Thinking Mode

DeepSeek v3のthinkingモードを内容に応じて切り替える:

| 条件 | thinking | 用途 |
|---|---|---|
| 短文（<10文字） | `False` | 挨拶・リアクション |
| light_patterns該当 | `False` | 「こんにちは」「ありがとう」等 |
| それ以外 | `True` | 複雑な推論が必要なリクエスト |

**重要**: `thinking=True` + `temperature=0` + 小さい `max_tokens` の組み合わせは、DeepSeekで `content` が空になる問題がある。分類・判定タスク（ResponseGate等）は必ず `thinking=False` で呼ぶこと。

#### ステップ別パラメータ

| ステップ | max_tokens | ツール | 備考 |
|---|---|---|---|
| 通常 | 1500 | 有効 | |
| 終盤（残り2ステップ） | 800 | 有効 | |
| 最終ステップ | 800 | **無効** | テキスト応答を強制 |

#### ステップインジェクション

ループ中にLLMの行動を制御するプロンプトを注入:

- **Step 0（複雑リクエスト）**: 「まず計画を立てて、何のツールを使うか考えてから実行」
- **通常**: 「ステップ N/M、残り R」
- **3ステップごと**: 反省プロンプト「元のリクエストに対して進捗は？同じツール繰り返してない？」
- **残り3ステップ以下**: 緊急プロンプト「達成できていれば最終回答を」
- **最終ステップ**: 「ツールを使わず、今までの結果をもとに最終回答してください」

#### エラー回復

- **ツール実行成功時**: 検証ナッジ「この結果は期待通りか？」を追記
- **同一ツール2回連続失敗**: 回復ヒント「別のアプローチを試すか、ユーザーに説明を」
- **同一ツール連続使用**: ループ防止警告「本当に繰り返す必要がありますか？」
- **Step 0でツール未使用**: ナッジ「ツールで対応できませんか？」で1回リトライ

#### Append-onlyコンテキスト

メッセージ配列は**追加のみ**。エラー履歴も削除しない。LLMは過去の失敗を見て別のアプローチを選択できる。

## 4. LLMプロバイダー

**ファイル**: `rajitan/agent/llm/base.py`, `rajitan/agent/llm/openai_provider.py`

### 抽象インターフェース

```python
class LLMProvider(ABC):
    async def chat_completion(
        messages, tools=None, temperature=0.7,
        max_tokens=1000, thinking=True
    ) -> LLMResponse

@dataclass
class LLMResponse:
    content: Optional[str]           # テキスト応答
    tool_calls: Optional[List[ToolCall]]  # ツール呼び出し
    usage: Dict[str, int]            # トークン使用量
    reasoning_content: Optional[str]  # DeepSeek thinking（ユーザーに見せない）

    is_final: bool      # content あり + tool_calls なし
    has_tool_calls: bool # tool_calls あり

@dataclass
class ToolCall:
    id: str
    name: str
    arguments: Dict[str, Any]
```

### Dual-LLM構成

```
DeepSeek v3 (deepseek-chat)          OpenAI (gpt-4o-mini)
  ↓                                     ↓
AgentOrchestrator                    OpenAIClient
ResponseGate                         要約・クイズ・音楽・感情分析
Agent Teams / サブエージェント
```

- `DEEPSEEK_API_KEY` 設定時: DeepSeekをエージェント用LLMに使用
- 未設定時: OpenAI `gpt-4o-mini` にフォールバック
- OpenAI APIは既存レガシー機能（要約・クイズ等）で継続使用

### DeepSeek Thinking Mode

OpenAI互換APIに `extra_body={"thinking": {"type": "enabled"}}` を追加して有効化。`reasoning_content` にDeepSeekの推論過程が入るが、ユーザーへの応答には含めない。

### 5.4 ToolRegistry

**ファイル**: `rajitan/agent/tools/base.py`

```python
class ToolRegistry:
    _tools: Dict[str, Tool]           # レガシー（Pythonクラス直接）
    _yaml_tools: Dict[str, ToolDefinition]  # YAML定義（現行方式）
    _executor: GenericExecutor        # YAML用実行エンジン
    _call_counts: Dict[str, int]      # 実行ごとの呼び出し回数
```

**機能**:
- **デュアルモード**: レガシーToolクラスとYAML定義の両方を管理
- **呼び出し回数制限**: ツールごとの `max_calls_per_execution` を強制

- **ユーザー別設定**: `apply_per_execution_config()` でツール無効化・上限変更

## 6. 3層記憶システム

**ファイル**: `rajitan/agent/memory/`

### アーキテクチャ

```
┌─ Tier 1: ワーキングメモリ（短期）─────────────────┐
│  保存先: メモリdict + Redis (TTL: 1時間)           │
│  内容:                                             │
│    ├── pending_actions: クイズ回答待ち、確認待ち等 │
│    └── context_notes: 一時的なメモ（最大5件）      │
│                                                     │
├─ Tier 2: アクションログ（中期）───────────────────┤
│  保存先: Redis (TTL: 6時間)                        │
│  内容:                                             │
│    └── actions: ツール使用履歴（最大20件）          │
│        tool_name, summary, timestamp, success       │
│                                                     │
├─ Tier 3: 永続記憶（長期）─────────────────────────┤
│  保存先: SQLite (agent_memories テーブル)           │
│  内容:                                             │
│    ├── user_preference: ユーザーの好み             │
│    ├── channel_trait: チャンネルの特徴             │
│    └── learned_fact: 学習した事実                  │
└─────────────────────────────────────────────────────┘
```

### 読み書きフロー

**読み込み**: `MemoryPromptIntegrator` → システムプロンプトに注入

```
トークン予算: ~700トークン（2100文字、日本語3文字≈1トークン）

優先度:
  1. Tier 1（常に全量）: pending_actions + context_notes
  2. Tier 2（直近5件）: アクション履歴
  3. Tier 3（残り予算で最大5件）: ユーザー記憶 + チャンネル記憶
```

**書き込み**: `AgentMemoryWriter` → `orchestrator.execute()` 完了後に自動実行

```
1. Tier 2: 使用ツール → アクションログに記録
2. Tier 1: quiz → QUIZ_ANSWERS 待ちアクション設定
           quiz_answer → 待ちアクション解除
3. Tier 3: よく使うツール → ユーザー傾向を記録
```

### メモリベースルーティングの仕組み

`on_message` で毎回 `has_pending_action(channel_id)` をチェック。高速パス（メモリdict → Redis）で低コスト。待ちアクションがあればメンションなしでもエージェントが起動し、マルチターン対話が可能。

## 8. コンテキストウィンドウ管理

**ファイル**: `rajitan/agent/context_manager.py`

### トークン推定

日本語テキストは `chars_per_token=3` で概算。`tool_calls` のJSONオーバーヘッドも考慮。

### 圧縮戦略

```
圧縮閾値: 80,000トークン（warning_threshold）

保持:
  [0] システムメッセージ（常に保持）
  [1] 元のユーザーメッセージ（常に保持）
  [-N] 直近Nメッセージ（keep_last_n_exchanges=4）

圧縮:
  中間のメッセージを要約:
  - アシスタント発言 → 100文字に切り詰め
  - ツール結果 → 150文字に切り詰め
  - 最新6エントリのみ保持（summary_keep_entries=6）

圧縮後:
  [system] + [user] + [圧縮サマリー] + [直近4メッセージ]
```

## 9. ResponseGate（品質ゲート）

**ファイル**: `rajitan/agent/response_gate.py`

### 2つの判定機能

#### 1. should_send — 応答品質チェック

エージェントの応答が「ユーザー向け回答」か「内部思考の漏れ」かを判定。

```
入力: エージェントの応答テキスト + ユーザーの元メッセージ
判定: LLMが YES / NO で回答（first-word exact match）
出力: True（送信する）/ False（ブロック）
フェイルセーフ: True（送信する）
```

- `thinking=False`, `temperature=0.0`, `max_tokens=5`
- タイムアウト: 10秒
- 「目的は達成できた」「次のステップとして」等の自己評価をブロック

#### 2. should_participate — 会話参加判定

会話ウィンドウ内でのメッセージに返事すべきかを三択で判定。

```
入力: 新しいメッセージ + 最近の会話
判定: LLMが YES / SKIP / LEAVE で回答
出力:
  "yes"   → エージェント起動して返事
  "skip"  → 無視（別の人に話しかけている等）
  "leave" → 会話ウィンドウを即時終了
フェイルセーフ: "skip"（無視する）
```

### 設計上の注意点

- **DeepSeek Thinking Mode は使わない**: 分類タスクで `content` が空になる問題がある
- **フェイルセーフは安全側**: `should_send` は送信、`should_participate` は無視
- **first-word exact match**: `"NO" in answer` の部分一致は誤判定が多発したため、先頭単語の完全一致に変更

## 11. サブエージェント（並列独立タスク）

**ファイル**: `rajitan/agent/team/`

### 概要

複数の**独立した**タスクを含むリクエストを自動分解し、同一仕様のサブエージェントで並列実行する。

```
「会話要約して、あとスケジュールも教えて」
  ↓
Planner.decompose() — LLMがサブタスクに分解
  ├── task_1: 会話要約 → [summary, get_conversation]
  └── task_2: スケジュール取得 → [schedule_list, get_current_time]
  ↓
asyncio.gather(SubAgent×2) — 並列実行
  ↓
Planner.synthesize() — 結果をらじたんの口調で統合
```

### メインエージェントとの違い

| 項目 | メインエージェント | サブエージェント |
|---|---|---|
| max_steps | 15 | 8 |
| thinking mode | 適応切替 | 常にoff |
| ツール | 全36 | タスク関連のみ |
| Discord操作 | 可能 | **不可** |
| call_counts | 共有 | **ローカルdict** |
| コンテキスト上限 | 80K tokens | 30K tokens |
| メモリ書き込み | あり | なし |

### フォールバック条件

以下すべてで単一エージェントにフォールバック:
- メッセージが30文字未満
- LLMが分解不要と判定
- サブタスク数が0-1個
- JSON解析失敗
- 全サブエージェントがタイムアウト
- 統合LLMが空レスポンス

### 設定（workflows/default.yaml）

```yaml
team:
  enabled: false
  max_sub_agents: 3
  sub_agent_max_steps: 8
  sub_agent_timeout_seconds: 60.0
  min_message_length: 30
```

## 12. Agent Teams（役割ベース協調）

**ファイル**: `rajitan/agent/teams/`

### 概要

異なる専門性を持つエージェントが、**依存関係のあるタスク**を協調して実行する。サブエージェントとの根本的な違いは、各チームメイトが**異なるロール・異なるツールセット**を持ち、**前段のタスク結果を後段が利用**できること。

### フロー

```
ユーザー: 「最近の会話の雰囲気に合う曲を選んで、理由も説明して」
  │
  ▼
[1] Leader.plan() — LLMがロール + タスク依存グラフを生成
    {
      "roles": [
        {"role_id": "researcher", "tools": ["get_conversation", "analyze_mood"]},
        {"role_id": "music_expert", "tools": ["music_search", "music_play"]}
      ],
      "tasks": [
        {"task_id": "task_1", "role": "researcher", "blocked_by": []},
        {"task_id": "task_2", "role": "music_expert", "blocked_by": ["task_1"]}
      ]
    }
  │
  ▼
[2] TaskGraph — Kahn's algorithmでWave計算
    Wave 0: task_1 (researcher) — 依存なし
    Wave 1: task_2 (music_expert) — task_1の結果が必要
  │
  ▼
[3] Wave実行
    Wave 0: researcher_1 → 会話履歴取得 → 雰囲気分析
            結果: 「ゲームの話が中心、楽しい雰囲気」
    Wave 1: music_expert_1 → 上流結果を参照 → 曲を選定
            結果: 「ゲーム系BGMを3候補選定」
  │
  ▼
[4] Leader.synthesize() — 全結果をらじたんの口調で統合
    「最近みんなゲームの話で盛り上がってるね！
     そんな雰囲気にピッタリの曲を選んだよ〜」
```

### コンポーネント詳細

#### TeamLeader (`leader.py`)

- **plan()**: LLMにロール定義 + タスク依存グラフの生成を指示（`thinking=False`, `temperature=0.3`）
- **synthesize()**: 全チームメイトの結果をキャラクター口調で統合（`thinking=False`, `temperature=0.7`）
- LLMの判断基準をプロンプトで明示（チーム使用/不使用のケース）
- 内部用語（「チーム」「サブエージェント」）を使わないよう指示

#### TaskGraph (`task_graph.py`)

```python
class TaskGraph:
    # Kahn's algorithmでWave番号を計算
    _compute_waves()   # Wave 0=依存なし, Wave N=max(依存wave)+1
    # 循環依存の検出 → CyclicDependencyError

    # アトミック操作（asyncio.Lock）
    claim_task(task_id, teammate_id)   # タスクを排他的に取得
    complete_task(task_id, result)     # 完了マーク → アンブロックリスト返却
    fail_task(task_id, error)          # 失敗マーク
    get_claimable(role_id=None)        # 実行可能タスク一覧

    # データアクセス
    get_wave_tasks(wave)               # 指定Waveのタスク
    get_upstream_results(task_id)      # 上流タスクの結果 {task_id: result}
```

#### TeamMailbox (`mailbox.py`)

チームメイト間のインメモリメッセージング（1実行のライフサイクル内）:

```python
send(from_id, to_id, content)     # to_id="all" でブロードキャスト
read(teammate_id, since=0.0)      # 自分宛のメッセージ取得
read_all()                         # 全メッセージ（リーダー統合用）
```

#### TeammateRunner (`teammate.py`)

ロール特化のエージェントループ。SubAgentRunnerと類似だが以下が異なる:

- **ロール固有システムプロンプト**: 専門性、タスク内容、上流結果、チームメンバー一覧
- **チームツール**: `team_report`（リーダーへ報告）、`team_message`（他チームメイトへメッセージ）
- **メールボックスチェック**: ステップ間で新着メッセージを確認し、コンテキストに注入
- **Self-claim**: 完了後、同一ロールの次のタスクを自動的に取得
- **ローカルcall_counts**: 並列安全（ToolRegistryの共有カウンターを使わない）
- **ツール呼び出し上限**: 1チームメイトあたり各ツール最大3回

**チームツール**（ToolRegistry外、TeammateRunner内でインライン処理）:

| ツール | 機能 | 処理 |
|---|---|---|
| `team_report` | リーダーに重要な発見・最終結果を報告 | Mailbox.send(→ "leader") |
| `team_message` | 他チームメイトに直接メッセージ | Mailbox.send(→ teammate_id) |

#### AgentTeamCoordinator (`team_coordinator.py`)

全体のライフサイクル管理:

```
1. leader.plan() → TeamPlan
2. TaskGraph構築（循環依存チェック）
3. Wave順に実行:
   for wave in range(max_wave + 1):
     ├── タスクをロール別にグループ化
     ├── ロールごとにTeammateRunnerを生成
     ├── asyncio.gather()で異ロール並列実行
     └── タイムアウト: teammate_timeout_seconds
4. leader.synthesize() → 最終応答
```

**Wave実行の並列性:**
- **異なるロール** → 並列（asyncio.gather）
- **同一ロールの複数タスク** → 1つのTeammateRunnerが順次処理（self-claim）

### チーム使用/不使用の判断

**LLMが判断**（leader.plan()のプロンプト内で指示）:

| 判定 | 条件 |
|---|---|
| **チーム使用** | 異なる専門性が必要、順序依存あり、大量情報の分業 |
| **チーム不使用** | 単純質問・雑談、1ツールで完結、全て独立タスク、タスク1個 |

**プログラム的フィルター:**
- メッセージ40文字未満 → 即スキップ
- ロール数 < 1 → スキップ
- タスク数 < 2 → スキップ
- 循環依存 → スキップ
- Wave数 > max_waves → スキップ

### フォールバック

以下すべてで `used_teams=False` を返し、次の判定段階（サブエージェント or 単一）にフォールバック:
- 計画LLMが空レスポンス
- JSON解析失敗
- `should_use_teams: false`
- タスク2個未満
- 循環依存
- Wave数超過
- 全体タイムアウト（180秒）
- 統合LLMが空レスポンス

### 設定（workflows/default.yaml）

```yaml
agent_teams:
  enabled: true
  max_teammates: 4            # 最大チームメイト数
  max_tasks: 8                # 最大タスク数
  teammate_max_steps: 8       # チームメイトの最大ステップ
  teammate_timeout_seconds: 90.0   # 個別タイムアウト
  overall_timeout_seconds: 180.0   # 全体タイムアウト
  plan_max_tokens: 1200       # 計画LLM
  plan_temperature: 0.3       # 低温: 正確な計画
  synthesize_max_tokens: 800  # 統合LLM
  synthesize_temperature: 0.7
  min_message_length: 40      # この文字数未満はスキップ
  max_waves: 4                # 最大Wave深度
```

### サブエージェント vs Agent Teams 比較

| 特性 | サブエージェント (`team/`) | Agent Teams (`teams/`) |
|---|---|---|
| ワーカーの種類 | 全員同じ汎用 | ロール別に専門化 |
| タスク関係 | 独立（並列のみ） | 依存関係あり（Wave順） |
| ツールセット | タスク関連のみ | ロール別に異なる |
| 前段結果の参照 | なし | 上流結果を自動注入 |
| エージェント間通信 | なし | Mailbox（team_report/team_message） |
| 実行順序 | 全並列 | Wave 0→1→2...（Wave内は並列） |
| 計画の複雑さ | サブタスクリスト | ロール定義 + タスク依存グラフ |
| 典型的ユースケース | 「要約して、スケジュールも教えて」 | 「雰囲気分析して、それに合う曲を選んで」 |
